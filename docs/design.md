# Trellis

This document outlines the design goals, specification structure, and a comparative analysis for **Trellis**. Trellis is designed as a minimal, normalized, and highly optimized format for LLM-based generation and updates.

## Design Goals & Constraints

Trellis is built around four core objectives:

*   **Multi-Artifact Single Source of Truth (SSOT):** Rather than bundling UI, API, database, and policy configurations directly in one massive file, this schema acts as the core data model. Other domain-specific schemas (e.g., OpenAPI definitions, UI layout files, or policy ontologies) import or reference the nodes and connectors defined in this schema.
*   **High LLM Fidelity:** **Fidelity** is defined as the measure of optimization for LLM-based generation and updates. Every structural choice in Trellis is optimized to maximize the probability that an LLM can successfully generate or update the schema without hallucinating structures, mismatching pointers, or desynchronizing bidirectional mappings.
*   **100% Deterministic Natural Language Translation:** The schema is designed so that a standard compiler can translate it into a perfectly accurate, human-readable English description. This allows humans to audit and verify schemas generated by LLMs without having to manually parse JSON.
*   **Minimal & Normalized Syntax:** Trellis adheres to a strict separation of nouns (Nodes) and verbs (Connectors), avoiding redundant declarations. To keep the core schema purely focused on structure, all presentation, display overrides, and localization concerns are decoupled and defined in a separate schema.

## Schema Specification

The formal schema structure is defined using standard JSON Schema syntax, authored in YAML. The latest specification is saved separately and can be viewed here:

### Core Components
1.  **`nodes`**: A map of entity types.
2.  **`connectors`**: A map of relationship types. Each connector defines its properties and its allowed topological `connections`.
3.  **`connections`**: An array of connections inlined *within* each connector, specifying the `from` and `to` nodes and their `cardinality` (using shorthand like `*`, `+`, `?`, `1` or range boundaries like `0..5`).

### Property Types & Validation via Embedded JSON Schema
To avoid reinventing a type and validation system, Trellis embeds standard **JSON Schema** directly within the `properties` block of nodes and connectors. This choice leverages standard JSON Schema features for:
*   **Built-in Types:** String, number, integer, boolean, array, and object.
*   **Formats & Constraints:** Support for standard formats (e.g., `uuid`, `email`, `date-time`) and validation limits (e.g., `minLength`, `maximum`, `pattern`).
*   **Required Fields:** Enforced via a standard `required` list alongside the properties block.
*   **Inheritance:** Model inheritance or composition can be represented using JSON Schema `allOf` and references (`$ref`).

### Semantic Uniqueness via `uniqueKeys`
Uniqueness is treated as a core semantic characteristic of a type (for example, the statement "an author's email address must be unique") and is decoupled from physical database implementation concerns. Trellis represents these constraints declaratively using an optional `uniqueKeys` array at the Node level.
*   It takes an array of arrays of strings: `uniqueKeys: [["propertyName"]]`.
*   This structure supports both **single-property uniqueness** (e.g., `[["email"]]`) and **composite uniqueness** (e.g., `[["firstName", "lastName"]]`).
*   Declaring these semantic constraints at the Node level maintains high LLM fidelity by keeping constraints simple, declarative, and isolated from nested property validation rules.

### Decoupling Display, Localization & Natural Language Output
To support multi-language localizations (L10n) and ensure the core Trellis schema remains strictly focused on logical data structure, all display overrides and natural language phrases are removed from the core schema.

Instead, display and localization mappings are defined in a separate localized catalog that references the type names in the Trellis schema. For example, an English translation schema would map the Trellis type `blog-post` to the singular `"blog post"` and plural `"blog posts"`, and the `editor` connector to the phrase `"is an editor of"`. 

This approach handles localization and natural language translation in the exact same manner as other target outputs—treating them as downstream consumers of the graph schema alongside API definitions, UI views, and database schemas.

## Example Schema

Below is a complete, validated example of a platform schema modeled in Trellis and authored in YAML. It utilizes hyphenated lowercase keys for domain elements (nodes and connectors) while preserving camelCase for schema keywords and node property names:

```yaml
$schema: https://specs.universal-graph-schema.org/v1/schema.yaml
name: blog-platform
nodes:
  author:
    properties:
      id:
        type: string
        format: uuid
      email:
        type: string
        format: email
      firstName:
        type: string
      lastName:
        type: string
    required:
      - id
      - email
    uniqueKeys:
      - - email
      - - firstName
        - lastName
  post:
    properties:
      title:
        type: string
        minLength: 1
      content:
        type: string
    required:
      - title
      - content
connectors:
  editor:
    properties:
      assigned:
        type: string
        format: date-time
    required:
      - assigned
    connections:
      - from: author
        to: post
        cardinality: "*..*"
```

### Detailed Format Evaluations

### Trellis
*   **Multi-Artifact SSOT:** Explicit separation of structural nodes/connectors from implementation concerns makes it easy for client MVC, API, and policy schemas to reference Trellis definitions.
*   **LLM Fidelity:** High change locality. Relationships are configured in a single connector block rather than duplicated inside nodes. Property types use standard JSON Schema, which LLMs are natively trained on. Direct string matching is used for connections instead of index pointers.
*   **Deterministic NL Translation:** Connector definitions map 1-to-1 to semantic templates. Localization and phrase overrides are decoupled, allowing multi-language translations without modifying the core logical structure.
*   **Human Verifiability:** Flat, clean structures are easy for humans to read and audit.

### [LinkML][]
*   **Multi-Artifact SSOT:** LinkML excels at multi-artifact generation, automatically compiling YAML declarations into SQL schemas, RDF, JSON Schema, and more.
*   **LLM Fidelity:** While LinkML reduces duplication, its slot-centric syntax is complex. The LLM must coordinate slot declarations, class declarations, and slot-usage mappings across different blocks, increasing error rates.
*   **Deterministic NL Translation:** Relies on third-party generators to compile natural language representations.
*   **Human Verifiability:** Highly readable YAML, though it becomes verbose for small property graphs.

### [GraphQL SDL][]
*   **Multi-Artifact SSOT:** Tends to conflate the data model with API execution concerns (directives, resolver queries).
*   **LLM Fidelity:** GraphQL's entity-centric view requires bidirectional relationships to be defined on both the source and target nodes. This duplication increases the probability of an LLM desynchronizing the relationship properties during updates.
*   **Deterministic NL Translation:** Relies on matching fields and comments, which is readable but lacks structured grammatical mapping primitives.
*   **Human Verifiability:** Exceedingly clean, type-based syntax that is highly intuitive for developers.

### [PG-JSON][] (Property Graph JSON)
*   **Multi-Artifact SSOT:** Hard to reference without an standardized schema wrapper.
*   **LLM Fidelity:** Lack of strict schema validation constraints causes the LLM's outputs to vary significantly.
*   **Deterministic NL Translation:** Provides basic node/edge definitions.
*   **Human Verifiability:** Simple, flat array of nodes and edges is readable.

### [JGF][]
*   **Multi-Artifact SSOT:** Designed as a data-interchange format; lacks built-in separation of schema and instance metadata.
*   **LLM Fidelity:** Lacks formal schema validation rules, forcing the LLM to invent its own property schema structures inside custom metadata blocks.
*   **Deterministic NL Translation:** Requires custom parsing logic for each unique metadata structure.
*   **Human Verifiability:** Standard graph layout is readable, but schema definitions are buried.

### [RDF / OWL][] (via JSON-LD)
*   **Multi-Artifact SSOT:** Excellent for semantic linked data, but difficult to map directly to client MVC code or REST endpoints.
*   **LLM Fidelity:** Extremely verbose restriction structures (`owl:Restriction`, `owl:maxCardinality`) lead to high syntax and namespace hallucination rates.
*   **Deterministic NL Translation:** Semantic predicates and ontologies map natively to natural language triples.
*   **Human Verifiability:** Heavily nested syntax is difficult to audit manually.

### [Neo4j Graph Schema][]
*   **Multi-Artifact SSOT:** Heavily coupled to database validation constraints.
*   **LLM Fidelity:** Relies on index-based pointers (`#/graphSchemaRepresentation/graphSchema/nodeLabels/0`) rather than direct strings. LLMs are notoriously bad at keeping track of relative index pointers, leading to broken schemas.
*   **Deterministic NL Translation:** Verbose structures are difficult to parse without preprocessing.
*   **Human Verifiability:** Normalized, highly fragmented layout is difficult to audit.
